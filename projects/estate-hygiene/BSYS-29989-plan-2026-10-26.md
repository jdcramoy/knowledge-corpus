Goal: one dedicated, capability-named Slack bot connection per capability, and retirement of the "My Workato genie slack connection NNN" series in Josh-gated batches.

The governing rules already exist and I am building on them, not inventing: workato-slack-bot-connections doctrine (never personal-user connections, net-new custom OAuth profile per capability, workspace-owned BT-approved Slack app, slack_bot connector for bot posts, scopes match the flow).

The read side is scriptable and I verified it live: the agentic API returns each Genie's triggers with the bound connection id (shared_account_id), so the inventory and the zero-caller proof are one scripted sweep each. The write side is the open question: the AIRO Genie tools expose no way to change an enablement's connection, so the re-map itself is UI work per Genie unless a probe of the raw API write path finds one first.

Phase 1, inventory (scripted): iterate the dev Genies, read each trigger's bound connection id, invert to connection-to-Genies, record last-used dates. Output: the connection audit table. Live proof this pass that inference would have lied: the HR Genie binds CON | Genie Slack Connection (22133279), not the series connection sitting in the same project. Project co-location is not evidence of binding; the trigger read is. That answers acceptance criterion 1 with verification instead of guesswork.

Phase 2, dedicated connections: one workspace-owned Slack app pattern per capability (for example [BTG] Slack Bot), net-new custom OAuth profile per provider type (slack vs slack_bot are provider-specific and the profile picker filters by provider), scopes matched to what the capability actually does. Built per the slack-bot-connection SOP.

Phase 3, re-map (probe first, then UI per Genie): probe the agentic write path for enablement connection changes once at build kickoff; if there is no surface, do it in the Genie settings UI, with the OAuth re-authorization the SOP requires. Verify each new binding by reading the trigger back. No unmapping until the new binding verifies.

Phase 4, retirement: Josh-gated batches only. Per batch: unmap the numbered connection, run a fresh scripted sweep proving zero Genies bind it (the audit is a snapshot, not a live guarantee), then delete with your explicit approval. Deletes are never automatic.

Phase 5, regrowth guard: add the dedicated-connection rule to the Genie-build SOP so every new enablement starts on a named connection.

Estimate: 3 points. Plan ready, awaiting your authorization to kick off the build. Same story was also filed as BSYS-29987 and BSYS-29988; suggest keeping this one and closing the copies.
